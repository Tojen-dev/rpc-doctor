# Synthetic v1 report fixtures

These files are independently authored examples, not captured provider benchmarks
and not generated by dropping fields from today's reports. Dates and timings are
fixed synthetic values for repeatable structural tests. They contain no endpoint
URLs, keys, headers, or provider messages. Every JSON file validates against
[`../../schemas/report-v1.schema.json`](../../schemas/report-v1.schema.json).

| Fixture | Purpose / independently checked expectations |
| --- | --- |
| `legacy-cli-v1.json` | Original public CLI shape at `c3a1358`; one healthy endpoint, unknown lag; no later additions |
| `legacy-warmup-v1.json` | Shape at `e1fc349`: reference, expected network, warm-up failure; no rounds, pacing, variability, or strict policy |
| `legacy-variability-v1.json` | Shape at `4c01814`: rounds, observations, sample count, stddev and p99; no strict policy |
| `success-v1.json` | Two healthy same-chain peers; chain ID and block height above JavaScript's exact integer range |
| `mixed-v1.json` | Two chain-1 peers, one partial failure with lag 5; a lone chain-8453 peer with null lag |
| `failure-v1.json` | Failed handshake plus an endpoint whose two measured attempts time out; no successful samples, null latencies |
| `strict-pass-v1.json` | Successful measured samples and warm-up, selected reference with unchecked lag, strict pass |
| `strict-fail-v1.json` | Rejected reference, warm-up and measured errors, positive pacing wait, strict failure reasons |
| `historical-outcomes-v1.json` | Four healthy baselines with independent found/null/unsupported/error probe outcomes; exact requested number above Number.MAX_SAFE_INTEGER; separate phase timing |
| `historical-skipped-v1.json` | Failed and wrong-chain handshakes; zero historical attempts, distinct skip reasons, null per-attempt times and zero phase duration |

The three historical examples were checked against the source at the named Git
commits. The compatibility claim is for these shapes, not every output of every
historical revision. Existing optional fields are checked when present; schema
validation alone cannot identify which revision produced a report. New CLI tests
also validate actual serialized reports for default/strict exit 0 and exit 1,
including the current local demo. Expected outcomes are asserted independently of
the schema; mutation tests assert rejection of malformed known fields.

Run from the repository root after `npm ci --ignore-scripts`:

```sh
npm run test:schema
npm run validate:report -- examples/reports/failure-v1.json
```

The second command succeeds: a valid report can describe a complete RPC failure.
These examples and the schema are included by `npm pack`; the validation helper
and Ajv are development tools in the source checkout, not runtime CLI requirements.
